and is anything left to agent diligence that could and should be mechanical?**

## Verified findings

### 1. The floor executes and bites — VERIFIED (ran it)
`pytest tools/tests/` → 42 passed, 1 skipped. `mdllm validate` on a deliberately
broken thing returned three correct Errors (missing `created`, undeclared status,
dangling `linked_things` reference) and exit 1.

### 2. The commit boundary enforces only `validate` — VERIFIED (read HOOK_BODY)
`tools/mdllm.py:1043–1066`: the pre-commit hook runs `mdllm validate "$ROOT"
--quiet` and nothing else. `install_hook` writes only `pre-commit`
(`tools/mdllm.py:1622, 1640`) — there is no commit-msg hook, so commit-message
conventions (`action: description`) are not mechanically enforced.

### 3. Mechanical checks that exist but the hook does not run — VERIFIED (argparse 1774–1847; each command run)
- `kernel --check` exists (`tools/mdllm.py:1815`); only a manual checklist item
  (`AGENTS.md:245`). Ran it: **"kernel: in sync," exit 0.**
- `index check` exists (`tools/mdllm.py:1783`); not in hook. Ran it: **in sync**
  (most indexes "not deployed," consistent with the opt-in design), exit 0.
- `provenance` exists (`tools/mdllm.py:1789`); enforces the quarantine rule in
  code; not in hook. NOT run live — the archive export has no `.git` and
  provenance needs git history; logic verified by reading only.

**Reading:** at this HEAD all three currently pass, so this is a gap in
*guarantee*, not a present defect. Integrity is guaranteed at commit; generated-
artifact freshness, provenance, and commit-message format depend on the agent
choosing to run the relevant command. The hook is the only surface that cannot
be forgotten — that is the argument for moving these onto it.

`orchestration.md:322, 366`. The committed tree describes two contradictory
mechanisms for writing the same artifact. Most likely the old prompt simply has
not been retired after the generator landed.

## Net

The mechanical/semantic boundary is drawn in the right place. The single
structural observation that survives scrutiny: enforcement is concentrated in
`validate` at the commit boundary, while `kernel --check`, `index check`,
`provenance`, and commit-message format are mechanised (or trivially
mechanisable) but only run when invoked — and all are clean at this HEAD, so the
gap is about guarantee, not a current break. Two small, freshly-verified
cleanups stand alongside it: the WORKLOG generated-vs-prompt contradiction
(finding 4) and the `stable` labels that no longer match reality (finding 5).

## Suggested order (lowest effort / highest guarantee first)

1. Retire or rewrite `worklog-update` so the session-end flow regenerates the
   WORKLOG (`mdllm worklog --write`) instead of instructing a hand-append —
   removes the contradiction in finding 4.
2. Add the `stable`-spec-recently-changed Info check to the floor (finding 5) —
   cheap, and it makes status drift self-surfacing.
3. Extend the pre-commit hook to also run `kernel --check` and `index check`
   (finding 3) — converts two generated-artifact checks from honour-system to
   guaranteed. Decide deliberately whether provenance joins them (it needs git
   history; weigh hook latency).
4. Consider a `coherence` check for the mechanical slice of the dark region
   (finding 6): foundational_specs ↔ filesystem, and catalog/Tier-2 coverage.
