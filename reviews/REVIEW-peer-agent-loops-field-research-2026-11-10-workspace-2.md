# Evidence backs the record, not the rulebook

Nobody has published the exact loop this plan describes (equal-status agents on four vendors' harnesses, coordinating through bare git with no server, no roster and no coordinator), but almost every part of it has a practised analogue, and the evidence sorts the plan cleanly into three piles. The record design is sound: keeping work state on the work item, one message per record, history in a log, steering at a tool boundary, and approvals that are cited instead of relayed all match what Gas Town, MCP Agent Mail, GitHub, Anthropic's harnesses and the security guidance already do. Three choices run against the evidence: carrying the contract as twelve prose rules in a skill with the mechanical aids left optional, accepting the operator's name on an unsigned commit as an approval, and typing a summon into Telegram as the operator. Three more enter territory with no published evidence either way: membership derived from commit authors, a ticket body replaced in place with history read from `git log`, and cross-vendor peers with no single lead. The strongest changes the evidence supports are to sign the operator's seat, to move the conversation rules out of the skill and into the wake payload and a refusing check, to put a deadline on every turn and every summon, and to give Codex an outer supervisor because it has no documented external wake. Most agent-specific numbers below are vendor-reported or preprints, and no controlled study tests turn-taking peers on a shared repository, so the plan's own measurements (396 answered handovers, 46 slow ones holding about 87 percent of waiting hours) are data the literature does not have.

## The field coordinates through records, short loops and one owner per task

Evidence labels used throughout: **[measured]** is a controlled result with stated numbers (preprints and workshop papers are flagged); **[vendor]** is a vendor's engineering post or internal evaluation, first-hand but not independently replicated; **[docs]** is vendor documentation of shipped behaviour, read but not tested hands-on by the researchers; **[spec]** is a protocol's normative text; **[practitioner]** is anecdote or opinion without data; **[guidance]** is published security or standards-body guidance that reports no data; **[secondary, unverified]** is a claim seen only through a summary. Two caveats from the researchers apply to everything that follows. Every harness statement is "the documentation says", fetched on 9 November 2026 and not observed to work. Protocol wording was extracted through a summarising fetch tool, so it is paraphrased here and should be checked against the linked page before being quoted.

### Shared-record tools keep the message out of the work item

The tools that coordinate coding agents through a repository or tracker have converged on one shape: a record per work item with owner and status as fields, and the conversation held somewhere else. Beads claims a task atomically by setting assignee and in-progress status together, and keeps messages as a separate record type with threading [docs] ([Beads README](https://github.com/steveyegge/beads)). Gas Town states the rule outright: the next session discovers state from the work records and not from mail, and routine traffic should be an ephemeral nudge because every mail is a permanent commit [docs] ([Gas Town mail protocol](https://github.com/gastownhall/gastown/blob/main/docs/design/mail-protocol.md)). MCP Agent Mail writes one markdown file per message into a git archive, with replies inheriting a thread identifier and an explicit `ack_required` flag [docs] ([mcp_agent_mail README](https://github.com/Dicklesworthstone/mcp_agent_mail)). GitHub's Copilot agent treats issue assignment as the turn token and a checklist in the pull request as state, with history left to commits and session logs [docs] ([GitHub Blog](https://github.blog/ai-and-ml/github-copilot/assigning-and-completing-issues-with-coding-agent-in-github-copilot/)). A practitioner pilot that uses the pull request as the bus arrived at the same split, with a local ledger recording only what was launched and GitHub holding outcomes; it reports no metrics [practitioner] ([TradersPost](https://blog.traderspost.io/article/github-as-the-bus-for-ai-agents)).

Almost all of these put a server, a database or a hosted platform in front of git: Gas Town starts a daemon set and Dolt, Agent Mail requires an MCP server with a SQLite index, and Copilot relies on GitHub itself [docs] ([Gas Town README](https://github.com/steveyegge/gastown); [mcp_agent_mail README](https://github.com/Dicklesworthstone/mcp_agent_mail)). The designs that are files in git and nothing else, such as Backlog.md, are single-agent or human-relayed [docs] ([Backlog.md README](https://github.com/MrLesk/Backlog.md)). The plan's serverless form is therefore a real departure in mechanism, not in idea.

### Vendors default to a lead, yet the measured gap between lead and peers is small

Anthropic's guidance and main products default to a lead that delegates, and it says most coding work has fewer parallelisable parts than research [vendor] ([Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). It has also published one flat experiment that is the closest analogue to this plan: 16 Claude agents with no orchestrator, claiming tasks by writing lock files into the git repository, built a 100,000-line compiler for just under $20,000, and the design failed on a monolithic task until the work was decomposed against a known-good oracle [vendor] ([Anthropic, Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)). That experiment was single-vendor and depended on a near-perfect test harness. Cursor is the counter-case: equal-status agents sharing a lock file fell to the throughput of two or three out of twenty, and without hierarchy no agent took responsibility for hard problems; Cursor moved to planners, workers and a judge [vendor] ([Cursor, Scaling long-running autonomous coding](https://cursor.com/blog/scaling-agents)). Cursor did not test equal peers with one named owner per task, and its scale was hundreds of agents.

The largest controlled comparison does not show hierarchy winning. Across 260 configurations, mean success was 0.466 for a single agent, 0.477 decentralised and 0.463 centralised, and on SWE-bench Verified every multi-agent variant scored slightly below the single agent [measured] ([Kim et al., arXiv:2512.08296 v3](https://arxiv.org/html/2512.08296v3)). Four caveats travel with that paper: "decentralised" there means all-to-all debate rounds, not turn-taking on a shared artefact; earlier versions are widely cited as covering 180 configurations, which the researchers did not verify; the v3 text contains an internal inconsistency about which architecture scored 0.282 on PlanCraft; and the widely quoted error-amplification figures (17.2x for independent agents against 4.4x centralised) are reported as not statistically significant after controlling for other metrics [measured] ([Kim et al., arXiv:2512.08296 v3](https://arxiv.org/html/2512.08296v3)). LangChain's benchmark found a peer-handoff design slightly ahead of a supervisor and traced the supervisor's deficit to paraphrasing when relaying; exact scores appear only in charts and the task was customer service, not coding [vendor] ([LangChain](https://www.langchain.com/blog/benchmarking-multi-agent-architectures)). Cognition's April 2026 position is the practical synthesis: several agents may contribute analysis and review, writes stay single-threaded, and unstructured negotiating swarms are mostly a distraction [vendor] ([Cognition, Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)).

### The open protocols solve a different problem

Agent2Agent reached its first stable version in March 2026 and moved into the Agentic AI Foundation in August 2026, alongside MCP and AGENTS.md [vendor] ([AAIF blog](https://aaif.io/blog/a2a-joins-aaif)). It is a two-role client and server protocol over HTTP in which every agent publishes a card and runs a reachable endpoint [spec] ([A2A specification](https://a2a-protocol.org/latest/specification/)). MCP's July 2026 revision moved further from peer messaging by removing sessions and server-initiated requests [spec] ([MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Neither defines a git or file binding, and the researchers found no published "A2A over git". The recurring published criticisms of A2A (no durable state, every agent an always-on service, no coordination model) come largely from a vendor with a competing product and should be read as advocacy [practitioner] ([HiveMQ blog](https://www.hivemq.com/blog/a2a-enterprise-scale-agentic-ai-collaboration-part-1/)). They are nonetheless the three things a git record supplies by construction, so the plan is not reinventing A2A; it addresses failure modes A2A leaves to the implementer. What the protocols do offer is a stable vocabulary, covered below.

"No published evidence" means the researchers found nothing that tests it.

### Peers over a shared record are supported at small scale and unmeasured across vendors

The plan's refusal of direct messaging departs from what the harnesses now ship: Claude Code has leaderless cross-session messaging and OpenClaw has `sessions_send` [docs] ([Claude Code cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging); [OpenClaw session tools](https://docs.openclaw.ai/concepts/session-tool)). The departure has support. Anthropic advises that agents write output to an external store and pass a lightweight reference, specifically to avoid a game of telephone [vendor] ([Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). A controlled coding study signals completion by git commit and not by status message, and names inconsistent views of shared state as the cause of late integration failures [measured, preprint] ([Geng and Neubig, arXiv:2603.21489](https://arxiv.org/html/2603.21489v1)). A single-author preprint reports that a shared, git-stored, append-only log cut redone work from 78% to 0%; its agent count and conditions could not be verified from the abstract [measured, single-author preprint] ([Sarkar, arXiv:2606.19616](https://arxiv.org/abs/2606.19616)).

The risk the evidence raises is ownership, not topology. Cursor's flat design failed partly because no agent owned hard problems, and the MAST taxonomy of 1,642 traces puts about 44% of failures in system design and found that giving one agent the final say raised task success by 9.4% on one framework [vendor; measured] ([Cursor](https://cursor.com/blog/scaling-agents); [MAST, arXiv:2503.13657](https://arxiv.org/html/2503.13657v3)). The 44% category total is the researchers' sum of per-mode figures, not a number printed in the text they retrieved. The plan's run already names each role to a seat, which is the per-task ownership Cursor never tested; the evidence says to make that naming unambiguous and to keep the reviewer out of the directing role, since Cognition has the agent that holds the task context decide which review findings to act on, and Cursor's single quality gate became a bottleneck [vendor] ([Cognition](https://cognition.com/blog/multi-agents-working); [Cursor, Towards self-driving codebases](https://cursor.com/blog/self-driving-codebases)). No study of heterogeneous-vendor peers coordinating through a repository was found.

### One message per ticket matches the principle; replacing the body in place is untested

Using a status to say whose turn it is has direct standard counterparts. A2A's input-required state and MCP's `input_required` result both mean the ball is in the other party's court, and LangChain's Agent Protocol forbids concurrent runs on one thread [spec; docs via search summary] ([A2A specification](https://a2a-protocol.org/latest/specification/); [MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog); [LangChain Agent Protocol](https://langchain-ai.github.io/agent-protocol/)). Because both standards have two fixed roles, neither can express an addressee among N peers, so the plan's "status names the seat" extends the idea instead of copying it.

The case for a short body is the best-measured part of the whole design. Focused inputs of about 300 tokens significantly outperformed full inputs of about 113,000 tokens on every one of 18 models, and topically similar distractors did the most damage [measured, vendor-authored] ([Chroma, Context Rot](https://www.trychroma.com/research/context-rot)). Multi-turn settings cost an average 39% against single-turn across more than 200,000 simulated conversations [measured] ([Laban et al., arXiv:2505.06120](https://arxiv.org/abs/2505.06120v1)). A stacked ticket body reproduces both conditions for every later reader.

The mechanism is where the plan is alone. Every surveyed tool that keeps one message per record does it by creating a record per message, which the plan refuses; none replaces a file body in place and relies on the path's git history. The one published anecdote of replace-in-place is adverse: in a file-based protocol between six Claude Code sessions, one agent saw only the second of two versions of an overwritten file, nothing polled automatically, and the author's fix was versioned files [practitioner] ([Rozenhek](https://dev.to/aviadr1/communication-protocols-for-ai-agents-that-cant-talk-to-each-other-b23)). The single-file conventions agents are most exposed to, OpenAI's ExecPlans and Anthropic's progress file, deliberately accumulate history inside the document, which gives a model a prior to append [vendor] ([OpenAI Cookbook](https://developers.openai.com/cookbook/articles/codex_exec_plans); [Anthropic, Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). The inference the researchers draw, and which this report adopts, is that writers stack because they cannot trust readers to consult history; the body rule therefore needs the reader side in place first. The tools that work hand the reader a bounded view: Agent Mail's `fetch_inbox` with a limit and `summarize_thread`, and Anthropic's harness opening each session with the last twenty log lines [docs; vendor] ([mcp_agent_mail README](https://github.com/Dicklesworthstone/mcp_agent_mail); [Anthropic, Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). The plan's rule 2 asks the agent to go and read; the evidence favours delivering the last few turns with the ring.

The field also keeps two things apart that the ticket status merges: the work item's lifecycle and the conversation's turn. Beads holds the first on the bead and the second in message records; GitHub holds the first in issue state and the second in review requests [docs] ([Beads README](https://github.com/steveyegge/beads); [GitHub Blog](https://github.blog/ai-and-ml/github-copilot/assigning-and-completing-issues-with-coding-agent-in-github-copilot/)). The plan moves lifecycle to the run, which achieves the same separation as long as ticket status carries only the turn.

### State on the run and pull request is the most settled element

This element matches practice everywhere the researchers looked. Gas Town's state-from-records rule, Anthropic's pass-a-reference advice, Copilot's checklist and the event-sourcing literature all say the same thing, and GitLab's guidance tells teams to keep the issue description current as the single source of truth when handing off [docs, seen as a snippet] ([GitLab blog](https://about.gitlab.com/blog/gitlab-tutorial-its-all-connected)). The plan's finding that 78 of 96 builder rounds restated pull request state corresponds to MAST's most frequent single failure mode, step repetition at 15.7%, which the authors class as a system design failure and not agent misbehaviour [measured] ([MAST, arXiv:2503.13657](https://arxiv.org/html/2503.13657v3)). Two cautions apply. No controlled experiment varies "status in one place" against "status mirrored in two". And the run record needs protection from the same stacking: Anthropic's harness lets later sessions change only one pass or fail field and chose JSON because, in its observation, a model is less likely to rewrite it than markdown, which is a vendor assertion and not a measurement [vendor] ([Anthropic, Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).

### A note is a steer, and every harness delivers it at a tool boundary

All four harnesses document the same behaviour for a message that arrives mid-turn: it waits until the running tool call finishes and is appended before the next model call, with a separate action for a hard interrupt. Claude Code reads a peer message between tool calls and starts a new turn if idle; Hermes's `/steer` lands after the next tool call; OpenClaw's default queue mode is steer and it names three intents (steer, followup, notify); Codex appends to an in-flight turn only through `turn/steer` on an app-server connection [docs] ([Claude Code cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging); [Hermes slash commands](https://hermes-agent.nousresearch.com/docs/reference/slash-commands); [OpenClaw queue and steering](https://docs.openclaw.ai/concepts/queue-steering); [Codex App Server](https://learn.chatgpt.com/docs/app-server)). The plan's word "interrupts" should become "steers": no harness cuts a running tool for a note. What a mid-task message means is the least specified part of the standards. A2A only permits agents to accept additional messages on a non-terminal task, and MCP has no method for unsolicited steering [spec] ([A2A specification](https://a2a-protocol.org/latest/specification/); [MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). The plan's rule that the holder states what the note changed is therefore new semantics in an open gap, with Agent Mail's acknowledgement call as the nearest precedent [docs] ([mcp_agent_mail README](https://github.com/Dicklesworthstone/mcp_agent_mail)). Two risks follow. A note delivered over git arrives only as fast as the doorbell can deliver into a running turn, which for Codex is not documented at all. And a note from any seat is untrusted input to an agent with tools, so it must never carry authority, which the plan's rule 7 already implies.

### Citing beats relaying, delegation is mainstream, and a bare name is not attestation

The principle that a go-ahead passed on by an agent is data and not authority is the best-supported idea in the plan. MCP forbids servers from relying on client-supplied user identification because it can be forged [spec] ([MCP elicitation](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation)). Claude Code tells the receiving agent that a peer message is not from the user and can never approve anything, and OpenClaw marks such messages as inter-session data [docs] ([Claude Code cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging); [OpenClaw session tools](https://docs.openclaw.ai/concepts/session-tool)). The Linux kernel's policy forbids AI agents from adding the human's sign-off tag [docs] ([kernel.org, AI coding assistants](https://docs.kernel.org/process/coding-assistants.html)). OWASP's 2026 agentic list names insecure inter-agent communication as a top-ten risk, though the item wording comes from secondary coverage and not the list's full text [guidance, wording secondary] ([OWASP landing page](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/); [TechRepublic](https://www.techrepublic.com/article/news-owasp-ai-agent-risk-list/)). The three mechanisms the requester saw refusing a relayed go on 6 November were behaving as the field intends.

Standing delegations are equally mainstream. The same object appears as a signed open mandate in Google's AP2, as typed authorisation details in RFC 9396, as an expiring delegation in UCAN, and as SLSA's "trusted robot" with an explicitly scoped standing exception [spec] ([AP2](https://ap2-protocol.org/); [RFC 9396](https://www.rfc-editor.org/rfc/rfc9396.html); [UCAN](https://github.com/ucan-wg/spec); [SLSA v1.2 Source](https://slsa.dev/spec/v1.2/source-requirements)). GitHub's September 2026 preview lets Copilot's review count as an approval only when an admin enables it, scopes it to file paths, and it is dismissed on new commits [docs, public preview] ([GitHub Changelog](https://github.blog/changelog/2026-09-01-copilot-code-review-can-now-approve-pull-requests)). The case for replacing per-action approval is vendor-measured: Anthropic reports users approve 93% to 97% of permission prompts, and that in a study of 1,053 paid testers humans caught 13.6% of dangerous commands against 89% for an automated classifier, with the human rate falling from about 17% to about 5% after 50 prompts [vendor] ([Anthropic, auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode); [Claude blog, auto mode default](https://claude.com/blog/auto-mode-default-in-claude-code)). These figures come from one vendor justifying a product decision, no methodology document was found, the 93% and 97% figures are not reconciled, and no independent replication exists. Anthropic itself still recommends human review for high-stakes changes. With about three in ten of the requester's coordination commits carrying a ruling, the volume is where reflexive approval is the expected outcome.

The unsigned name is the exception. Git's manual says of the author name: "This name has no effect on authentication" ([git-commit documentation](https://git-scm.com/docs/git-commit)). Any process with write access sets it through two environment variables, so an unsigned operator-named commit is cryptographically no stronger than a relayed quote. The industry's answer for consequential delegations is a signature by the human: AP2 mandates are signed credentials, and GitLab offers re-authentication at approval time and describes it as an electronic signature [spec; docs] ([AP2](https://ap2-protocol.org/); [GitLab approval settings](https://docs.gitlab.com/user/project/merge_requests/approvals/settings/)). The field also binds an approval to the exact revision and dismisses it on change [docs] ([GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)), which a commit-based approval reproduces only if it cites the SHA it approves.

### Derived membership has no precedent and inherits known costs

Every surveyed tool with a notion of "who is here" maintains a declaration: Agent Mail's `register_agent`, Claude Code's `members` array, A2A's mandatory Agent Card [docs; spec] ([mcp_agent_mail README](https://github.com/Dicklesworthstone/mcp_agent_mail); [Claude Code agent teams](https://code.claude.com/docs/en/agent-teams); [A2A specification](https://a2a-protocol.org/latest/specification/)). None requires a central registry, and A2A's own documentation lists a registry's maintenance burden as a drawback, so the plan's objection is shared [spec docs] ([A2A Agent Discovery](https://a2a-protocol.org/latest/topics/agent-discovery/)). The registry designs have their own stale-member failure: after a resume, a Claude Code lead can try to message teammates that no longer exist [docs] ([Claude Code agent teams](https://code.claude.com/docs/en/agent-teams)). That is the argument for trying derivation, but no published design derives agent membership from commit history and reports how it behaved.

The costs are predictable from classical work. A commit history records who has spoken, not who is alive; gossip protocols such as SWIM added probing and a suspect state for exactly that reason, though the researchers read SWIM only through summaries [secondary] ([SWIM paper, course copy](https://courses.grainger.illinois.edu/cs425/fa2022/dsn02-SWIM.pdf)). Identity is whatever the writer claims unless signed, and GitHub marks a commit verified only when a signature checks out [docs] ([GitHub commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification)). The plan's own first read already shows alias drift: one seat under two names, two clones declaring the same seat, and several hundred commits under the operator's identity. Git's built-in answer to aliases is a mailmap file [canonical, not re-fetched] ([gitmailmap](https://git-scm.com/docs/gitmailmap)), which is a defined list. The honest reading is that "derive, never define" holds for presence and activity but cannot hold for authentication, which needs at least a list of trusted keys. The plan is also less pure than its slogan: each clone declares its seat, and each run names roles to seats, which is A2A's "direct configuration" discovery under another name.

### Starting from one seat works; the receipt needs a deadline and the summon must not impersonate

Launching other vendors' agents from one place is established. OpenClaw documents spawning Claude Code, Codex and Gemini CLI sessions through its ACP backend; AWS's CLI Agent Orchestrator lists ten providers including Hermes; Gas Town injects mail through hooks where the runtime has them and uses a startup fallback for Codex [docs] ([OpenClaw ACP agents](https://docs.openclaw.ai/tools/acp-agents); [CAO docs](https://awslabs.github.io/cli-agent-orchestrator/docs/intro); [Gas Town README](https://github.com/steveyegge/gastown)). Each of those makes the launcher an orchestrator. The plan's starter that steps back has thinner support: Anthropic's long-running harness uses an initializer session that differs from later sessions only in its first prompt [vendor] ([Anthropic, Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)), while Claude Code's team lead cannot be transferred at all [docs] ([Claude Code agent teams](https://code.claude.com/docs/en/agent-teams)).

Taking the first commit as the receipt is the right response to a documented weakness. No push path acknowledges delivery: Claude Code channels drop events silently if the session has not loaded the channel and the documentation tells builders to carry their own confirmation; OpenClaw's HTTP 200 means admission only [docs] ([Claude Code channels reference](https://code.claude.com/docs/en/channels-reference); [OpenClaw webhooks](https://docs.openclaw.ai/automation/cron-jobs/webhooks)). A receipt that never comes is a lost token, so it needs a timer. Published loops are bounded mechanically and tightly: Microsoft's Magentic sample uses 10 rounds and 3 stalls, and Claude Code overrides a blocking Stop hook after eight consecutive blocks [docs] ([Microsoft Learn, Magentic](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/magentic); [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)). The plan's twelve rules contain no round cap; the draft refers to an existing stall ring whose mechanics this research did not examine.

The surfaces differ more than the plan's table suggests. Claude Code documents that an `asyncRewake` hook exiting with code 2 wakes even an idle session, and that in a non-interactive run a background command's exit gives Claude one more turn; the researchers found no sentence stating the same for an idle interactive session [docs] ([Claude Code hooks reference](https://code.claude.com/docs/en/hooks); [Claude Code headless](https://code.claude.com/docs/en/headless)). Unattended sessions cap background commands at 30 minutes by default and two hours at most, and background tasks are not restarted on resume [docs] ([Claude Code tools reference](https://code.claude.com/docs/en/tools-reference); [Claude Code scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)). Hermes documents a background process whose completion starts a new turn, and also a cron tick every 60 seconds with a script that can decline to wake the agent, which does not depend on a long-lived process [docs] ([Hermes messaging gateway](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/); [Hermes cron](https://hermes-agent.nousresearch.com/docs/user-guide/features/cron)). OpenClaw, which the plan lists as having no doorbell, documents a wake endpoint and ordinary automation jobs [docs] ([OpenClaw webhooks](https://docs.openclaw.ai/automation/cron-jobs/webhooks); [OpenClaw heartbeat](https://docs.openclaw.ai/gateway/heartbeat)). Codex is the gap: the researchers found no documented way for an external event to start a turn in a local Codex CLI session, its `notify` setting is outbound only, its event triggers work only on web and mobile, and its MCP server mode has been removed [docs] ([Codex hooks](https://learn.chatgpt.com/docs/hooks); [Codex advanced config](https://learn.chatgpt.com/docs/config-file/config-advanced); [Codex scheduled tasks](https://learn.chatgpt.com/docs/automations?surface=app); [Codex MCP server page](https://learn.chatgpt.com/docs/mcp-server)). The summon-as-operator question is answered in the open-questions section.

### Twelve rules in a skill is the element the evidence opposes

The plan's own record is the first exhibit: rules 1 to 3 were written and not followed on three containers across two months. Published evidence explains why. A skill's body is loaded only when the model judges it relevant [vendor] ([Anthropic, Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)). In Vercel's evaluation the skill was never invoked in 56% of cases and scored the same 53% as no skill at all, while the same content placed passively in AGENTS.md scored 100%; the model and task count are not stated [vendor] ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)). Claude Code's documentation says instruction files are treated as context and not enforced configuration, and that anything that must happen at a fixed point should be a hook [docs] ([Claude Code memory](https://code.claude.com/docs/en/memory)). In the closest controlled analogue to "a rule in a file against a mechanism", coding agents constrained only by instruction scored 3.0 to 7.8 points below the same constraint expressed as git worktree isolation [measured, preprint] ([Geng and Neubig, arXiv:2603.21489](https://arxiv.org/html/2603.21489v1)). Claude Code's own team feature concedes that instruction-only status updates lag and offers hooks that refuse the transition as the fix [docs] ([Claude Code agent teams](https://code.claude.com/docs/en/agent-teams)). Cursor asserts the opposite, that prompts mattered more than harness, but the fixes it reports are structural [vendor] ([Cursor](https://cursor.com/blog/scaling-agents)).

The evidence is equally clear that more prose is not the answer. Instructions that are in context are followed (a tool named in a context file was used 1.6 times per task against fewer than 0.01 when unnamed), yet context files produced no significant gain in task success and raised cost by roughly 20% [measured] ([Gloaguen et al., arXiv:2602.11988](https://arxiv.org/html/2602.11988)). The two aids the plan calls optional are the supported part. Requirements that were re-cued through tool traffic held at 89% to 100% adherence while those stated once early fell to 22% to 32% after compaction, and a single mid-trajectory restatement was worth 5.6 points with further restatements adding nothing [measured, workshop paper; primary model not named] ([Kirste and Kropiunig, NeurIPS 2026 workshop](https://neurips.cc/virtual/2026/176245)). Two lines riding on every ring is exactly that class of cue, and one restatement per wake is the dose the data supports. No controlled study compares a standing file, a point-of-action reminder and a hard validator head to head, so the ranking between the last two rests on vendor guidance. One further exposure: Claude Code's `--bare` mode skips hooks, skills and CLAUDE.md, and its documentation says bare will become the default for non-interactive runs [docs] ([Claude Code headless](https://code.claude.com/docs/en/headless)). A seat summoned that way would load neither the skill nor the hooks, which is another reason for the rule to travel in the wake message.

### The requester's measurements fill a gap the literature leaves

The researchers found no published data on turn latency in agent-to-agent loops, no controlled comparison of a full transcript against "latest message plus log pointer", and no report of agents stacking a conversation past 100,000 characters. The plan's numbers are therefore primary data, unverified by this research. The brief for this report describes one conversation of roughly 200 rounds; the draft's own table gives 78 of 96 builder rounds on one lane and a run with 294 commits, and this report uses the draft's figures. They are consistent with published mechanisms. Two thirds of handovers answered within fifteen minutes with 46 slow ones holding 415 of 479 waiting hours is the profile of a turn-taking design gated by an absent participant; Anthropic describes a synchronous lead blocked by one slow subagent [vendor] ([Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). The researchers found that published repetition detectors and iteration caps address an agent that is busy but unproductive, not one that is not running, and found no source describing leases or heartbeats for LLM agents with measured results. A lane of 96 builder rounds is far outside published practice: Anthropic's generator and evaluator ran 5 to 15 iterations before scores plateaued [vendor] ([Anthropic, Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). Because the baseline exists, the plan can do what the field has not: measure the same quantities after the change.

## Four open questions, four direct answers

### Attestation: require a signature, verified by code, on a key the agents cannot use

The operator's name alone is not enough, and the evidence here is the strongest in the report because it is a property of git and not an opinion. An unsigned commit under the operator's name moves the relay from the message body to the header. Sign the operator seat's commits, at minimum every approval and every standing delegation. GitHub verifies GPG, SSH and S/MIME signatures and can require signed commits on a branch [docs] ([GitHub commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification); [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). Sigstore's keyless gitsign is not shown as verified by GitHub, so it is the wrong tool if the badge matters [docs] ([sigstore/gitsign](https://github.com/sigstore/gitsign)). Three conditions make the signature mean something. The check should run in deterministic code and not in each agent's reading of the record, which is OWASP's complete-mediation advice [guidance] ([OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)). Each approval should cite the exact SHA it approves. And the key must be one the agents cannot use, which is the researchers' inference from the mechanics and not a sourced claim. Two details were not source-checked and need verifying before design: git's repository-local allowed-signers mechanism, which is what a forge-independent check would use, and signed tags as a carrier for a ruling over a whole tree. A single-operator estate cannot reach two-person review in SLSA's sense, and GitHub does not count the tasking human's approval of an agent's pull request as independent, a statement the researchers saw only through a search result [docs, via search] ([About Copilot coding agent](https://docs.github.com/copilot/concepts/coding-agent/about-copilot-coding-agent)).

### A summon must not be sent as the operator

Every vendor page the researchers read points the same way. Claude Code and Hermes both gate their messaging channels on the sender's identity, so a line typed in the operator's Telegram account arrives with the operator's authority whatever it says [docs] ([Claude Code channels reference](https://code.claude.com/docs/en/channels-reference); [Hermes messaging gateway](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/)). Hermes states the limit of its own check: authenticating a webhook sender does not authenticate the content [docs] ([Hermes webhooks](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/webhooks)). In RFC 8693's terms an agent typing as the operator is impersonation, and the OpenID Foundation's whitepaper, which is a proposal and not a standard, recommends replacing impersonation with delegation in which the agent keeps its own identity [spec; proposal] ([RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.html); [OpenID Foundation, arXiv:2510.25819](https://arxiv.org/html/2510.25819v1)). "The line carries no authority" is a property of the plan's intent that the receiving harness cannot see. Automating a personal Telegram account also carries a higher ban risk than a bot account, per a library's documentation [secondary] ([Telethon docs](https://docs.telethon.dev/en/v2/basic/next-steps.html)).

The alternatives already exist. Hermes can ring itself with a cron job whose script watches the remote ref, or with a background process that starts a turn on exit. If a push is wanted, a Hermes webhook route with its own HMAC secret lets the starter seat summon under its own identity. Telegram's 2026 bot-to-bot mode would allow a distinct bot for the starter seat, but Telegram's own FAQ still contradicts its newer API page, and whether either harness's allowlist accepts a bot sender is unverified [docs] ([Telegram bot-to-bot](https://core.telegram.org/api/bots/bot-to-bot); [Telegram Bots FAQ](https://core.telegram.org/bots/faq)).

### Branch per conversation: park it, and keep branches for work items

The research did not examine the branch-per-conversation plan itself, so this answer rests on the surveyed evidence. Branch or worktree isolation has a measured benefit for code: worktree-isolated agents beat instruction-isolated ones [measured, preprint] ([Geng and Neubig](https://arxiv.org/html/2603.21489v1)), and Copilot works on one branch and one pull request per task [docs] ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)). That is a branch per work item, which the plan keeps through the pull request. For conversations the precedents are git-bug and Gerrit NoteDb, which put each entity's log on a dedicated ref, never in a working branch, and rely on an index or cache for reads. That is more machinery than this plan wants. The one anecdote of messages spread across branches needed a human to trigger every read [practitioner] ([Rozenhek](https://dev.to/aviadr1/communication-protocols-for-ai-agents-that-cant-talk-to-each-other-b23)). The benefit a branch would bring, an isolated ordered history per conversation, is already available from the history of one file per ticket. No source measures merge-conflict rates for either layout, so the evidence is thin in both directions: park it, and reopen only if ticket files start to conflict under concurrent writers.

### Run Step 1 in the two substrate clones, then measure in the engineering workspace

The two questions Step 1 answers need different places. Whether the mechanism works (a ticket crosses, a note lands mid-task, the body stays a page, the owed round trip completes) is best tested where nothing else is moving, and Anthropic's guidance is to start minimal and extend on observed failure [vendor] ([Anthropic, context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Clean clones also remove a confound: an existing stacked body is itself an in-context exemplar, and Manus reports, without measurements, that models imitate repeated patterns in context [practitioner] ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)). Whether the rules hold under load cannot be shown there. The clones are same-vendor and same-machine, so they exercise neither the Codex wake gap nor long lanes, and compaction, which silently drops requirements stated once early, only bites on long work [measured, workshop paper] ([Kirste and Kropiunig](https://neurips.cc/virtual/2026/176245)). Vercel's finding that rewording an instruction flipped outcomes means a rewritten contract has to be judged against observed behaviour [vendor] ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)). So: prove the mechanism in the substrate clones, and treat adherence as unproven until one fresh lane in the engineering workspace, started on new tickets, is read back against the existing baseline of body size, the slow-handover tail and the share of relayed rulings.

## Conclusion

The research changes what kind of project this is. The plan presents itself as a contract with a little optional code; the evidence says the contract is the part that has already failed and the "optional" code is the part with published support. That does not mean building a coordinator. Every mechanical fix the evidence favours (a signature check, a wake payload, a refusing size check, a deadline) is small, sits at an existing boundary, and leaves the peers equal. The plan's refusals survive intact except one: a system that will not define a roster still has to define whose keys it trusts.

The plan is also in a position the field is not. No one has published latency distributions, body-growth data or relay rates for agents taking turns on a shared record, and the requester holds a two-month baseline of exactly that. If each build step is read back against the same measures, the result will be the first before-and-after evidence on whether one message per record, state on the work item and cited authority reduce waiting and relaying in a cross-vendor peer loop. Three claims deserve explicit tests because nothing published settles them: that agents will read history from git when it is delivered instead of requested, that commit-derived membership stays accurate without a registry, and that a starter can step back without drifting into the coordinator's role.
