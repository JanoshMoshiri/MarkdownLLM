# Leaders wake agents on artefacts, not conversations

## Corrections from the operator, 2026-11-13

Read back in session the day it was written. The operator's hands-on record
overrides two of the report's inferences, and states what the loop is for.

- **Codex's wake is not this loop's largest gap.** A Codex desktop session
  told to keep its watcher bound inside its own session holds it for 24 to
  48 hours. The report's Codex finding is about waking a desktop thread
  *from outside*, which this loop does not need while each seat binds its
  own watcher. The failures seen in practice had two other causes: Codex
  reading "keep watching" as a scheduled heartbeat task, which has always
  failed; and watches on a resource-starved machine, running a local CI
  runner in place of a hosted one, that timed out. So the loop's start
  instructions should always say *bind the watcher in this session, never a
  scheduled heartbeat*, so the operator does not have to remember to.
- **The loop-guard inference is a check, not a cause.** A starved machine
  explains the failures at four to five concurrent loops at least as well,
  and is cheaper to rule out first.
- **The loop's value is validation, not throughput.** Controlled studies find
  multi-agent coding neutral to slightly negative at several times the
  tokens. The operator runs cross-vendor loops for the reason science runs
  peer review. The opening this report names is the one the operator means
  to pursue as an eval: nobody has published the catch rate of cross-vendor
  review against same-model review with the reviewer isolated from the
  author's verdict.

The report follows as written, its first line excepted.

Nobody in 2025-2026 runs a loop shaped like ours, cross-vendor and local and with the human present in every live session, but different leaders have each solved one part of it well. GitHub's Agent HQ has the only working place where agents from different vendors meet. You wake Claude, Codex or Copilot by assigning an issue or mentioning the agent on a pull request, and a commit trailer links each change to its session log. Anthropic's Claude Code has the most complete way to wake an agent inside a live session the human can see. Peer messages arrive between tool calls, they start a turn if the session is idle, they show as a visible line, and they can never count as the user's consent. Cognition's coordinating Devin and Google's Antigravity inbox show how a single human supervises many agents. Hermes and similar messaging gateways show how a local agent can be woken without exposing a public endpoint. Microsoft's Agent Framework is the clearest case that topology can be swapped, provided one component owns "who speaks next" and a hard cap ends the run. OpenAI is the laggard for our purposes. Codex now has a stable `codex queue` command that wakes an idle session, but the desktop app keeps its server private and lets only one writer touch a thread. A relay-free doorbell into a Codex desktop thread therefore remains unsupported, which explains our hand-relayed doorbells. The controlled evidence says three things. Topology must match the task. Hubs contain errors better than peers. Per-agent capacity thins beyond three or four agents, which matches our wakes failing at four or five loops. Three problems are unsolved everywhere: switching between orchestrated and peer modes at runtime, keeping a human's direct word to one agent from crossing another agent's turn, and keeping a reviewer independent of the author's conclusion. Our git-backed, cross-vendor, turn-token record is ahead of every product's vendor-hosted log. We are behind on bounded, deduplicated, acknowledged wakes, on a single "who is waiting on me" surface for the human, and on reviewer isolation.

## Five leaders each own one slice of the problem

The coding products have settled on one shape: an orchestrator-worker star, in which a coordinator or a human sends work out to isolated workers that do not talk to each other. The frameworks, by contrast, ship several topologies side by side. Where each leader excels is narrower than its marketing suggests, so the useful question is what each one does better than anyone else.

| Leader | What it does best | Lesson for us | Source |
|---|---|---|---|
| GitHub Agent HQ | Cross-vendor meeting place: Claude, Codex and Copilot assignable on one issue; `@claude`/`@codex` comments re-wake them; mid-session steering applied after the current tool call; `Agent-Logs-Url` commit trailer | The shared artefact is the protocol, and the platform's own event is the wake | [GitHub Changelog](https://github.blog/changelog/2026-02-04-claude-and-codex-are-now-available-in-public-preview-on-github/); [GitHub Docs](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents) |
| Anthropic Claude Code | Waking a live, visible session: cross-session messaging on by default, channels, self-wake, Remote Control; agent teams with peer mailboxes and a file-locked task list | Separate *who may wake an agent* from *what a message may authorise* | [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging); [Agent teams](https://code.claude.com/docs/en/agent-teams) |
| Cognition Devin | A coordinator with a session link per child, direct messages to any child, self-scheduled check-ins, per-child compute caps, about ten children at a time | Bounded concurrency plus a self-wake over shared state | [Cognition blog](https://cognition.com/blog/devin-can-now-manage-devins); [Devin docs](https://docs.devin.ai/product-guides/advanced-mode) |

Two other leaders matter for narrower reasons. LangChain measured the cost of a hub that paraphrases. Its supervisor design lost slightly to a peer-handoff "swarm" because the supervisor rephrased what sub-agents said. Letting sub-agent replies pass through verbatim, and stripping handoff chatter, improved the supervisor by **nearly 50%** on the vendor's own benchmark ([LangChain](https://www.langchain.com/blog/benchmarking-multi-agent-architectures)). Amp is the one product that routes review to a different model family by design: its Oracle is a read-only subagent on an OpenAI model inside an otherwise Anthropic-driven tool ([Amp: Oracle](https://ampcode.com/news/oracle)). The laggards also teach something. OpenAI's coordination is parent-owned in both of its products, and the open issues filed by integrators trying to coordinate Claude Code and Codex in one repository are the clearest public record of the gap we are living in ([Issue #54683](https://github.com/openai/codex/issues/54683)).

## Stars contain errors, peers lose less in relay, and nobody switches at runtime

### The controlled evidence says topology must fit the task

The largest controlled study, **260 configurations** across six benchmarks and three vendors' models, found that the mean effect of going multi-agent was **-0.3%**, with a 95% confidence interval from -58.7% to +77.2%. The sign depends on the task. Centralised orchestration gained **+80.8%** on parallelisable financial analysis. Every multi-agent topology lost **39% to 70%** on sequential planning. All of them were neutral or slightly negative on SWE-bench Verified ([Kim et al., arXiv 2512.08296](https://arxiv.org/html/2512.08296)). Gains vanished once a single agent already scored above about 45%. Turn count grew super-linearly with agent count, and the authors describe per-agent reasoning capacity as "prohibitively thin" beyond **three to four agents**. Trace-level error amplification was **4.4x** for centralised systems against **17.2x** for independent agents, though those terms were not significant once overhead was controlled ([Kim et al.](https://arxiv.org/html/2512.08296)). Anthropic's own research system agrees on the parallel-breadth case: a lead with subagents beat a single agent by **90.2%**. It also says token spend alone explained **80%** of performance variance, and that "most coding tasks" are a poor fit ([Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)). By January 2026 Anthropic's guidance had narrowed to three justifications (context pollution, parallel tasks, specialisation) at a cost of **3-10x** the tokens of a single agent ([Claude blog](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)).

Our star is the right default on this evidence, for a reason that has little to do with speed: the hub is where verification sits, and centralised verification is the topology that contains errors best. The same evidence warns that a hub costs fidelity if it paraphrases. LangChain's measured fix, forwarding verbatim, is exactly what a ticket record does when the hub cites the spoke's committed words instead of retelling them.

### Pure peers fail on ownership, not on talking

Anthropic's one published peer experiment ran 16 Claude agents with no orchestrator. They claimed tasks by writing lock files into git, a `while true` loop relaunched each agent, and the result was a 100,000-line compiler for just under $20,000. It worked only because "the task verifier is nearly perfect", and it broke on a monolithic task until the work was decomposed against a known-good oracle ([Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler)). Cursor's flat design failed for a different reason: without hierarchy, no agent took responsibility for hard problems ([Cursor](https://cursor.com/blog/scaling-agents)). Cognition's synthesis is that several agents may analyse and review, but writes stay single-threaded ([Cognition](https://cognition.com/blog/multi-agents-working)). The MAST taxonomy of **1,642 traces** found that giving one agent the final say raised task success **9.4%** on one framework ([Cemri et al., arXiv 2503.13657](https://arxiv.org/html/2503.13657v3)). The pattern across all four is that peers need one named owner per piece of work and a strong verifier. Messaging between them is not the hard part.

### Switching is done by humans and code, not by the system

The frameworks make topology a choice but not a runtime decision. In Microsoft's Agent Framework, Group Chat "assembles agents in a star topology, with an orchestrator in the middle", and a selector function, an orchestrator agent or a custom manager picks the next speaker. Handoff, the alternative, lets agents "directly transfer control" ([MS Learn](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/group-chat)). The developer picks one when building the workflow. Kim et al. built a regression that chose the best architecture for **87%** of held-out configurations, but it is an offline predictor, and the researchers found no controlled study of systems that switch topology mid-task ([Kim et al.](https://arxiv.org/html/2512.08296)). Claude Code's agent teams are the most instructive hybrid. Teammates message each other directly, and the human can talk to any of them. Yet the lead is fixed for the session's lifetime, holds every permission prompt, and cannot hand leadership to anyone else ([Agent teams](https://code.claude.com/docs/en/agent-teams)). The field has not built a switch between star and peer. It has separated two topologies that we have been treating as one: messages may flow peer to peer while authority stays a star.

## Waking a live session works on Claude, works through a gateway on Hermes, and stalls on Codex desktop

### Every working meeting place wakes agents with its own event

In every place cross-vendor agents actually meet, the host platform wakes them: an issue assignment, an @mention, a Slack message. The conversation's state lives in the platform object, not in the agent ([GitHub Changelog](https://github.blog/changelog/2026-02-04-claude-and-codex-are-now-available-in-public-preview-on-github/); [Slack blog](https://slack.com/blog/news/agent-first-workspace-slack)). Cursor Automations and Factory generalise this into triggers on schedules, Slack, Linear, GitHub and webhooks ([Cursor docs](https://cursor.com/docs/automations); [Factory docs](https://docs.factory.ai/software-factory/automations.md)). This is the reverse of A2A, where each agent is a reachable web service holding task state. A2A's push notifications require that the client "must be reachable via HTTP", and its streams "MUST NOT be considered a reliable delivery mechanism" ([A2A Specification](https://a2a-protocol.org/latest/specification/)). A Claude Code or Codex session on a laptop behind NAT, alive only while a human has it open, fits A2A badly on either end. Hermes shows the alternative. One gateway process dials out to Telegram, Slack and a dozen other platforms, maps each chat to a session, and runs a cron scheduler every 60 seconds ([Hermes messaging docs](https://hermes-agent.nousresearch.com/docs/user-guide/messaging)). A pre-run cron script can return `{"wakeAgent": false}` to skip a tick, which makes a cheap watch on a git ref possible without a long-lived watcher process ([Hermes cron](https://hermes-agent.nousresearch.com/docs/user-guide/features/cron)).

### Claude Code has the most complete in-session wake

Since v2.1.224 (v2.1.234 on native Windows), Claude Code sessions can message each other with nothing to enable. "The receiving Claude reads the message between tool calls during an active turn. When the receiving session is idle, Claude Code starts a new turn with the message." The human sees a dim one-line preview and can expand it ([Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)). Delivery on the same machine goes over a per-session socket or named pipe, and scripts and hooks can post to it through `CLAUDE_CODE_MESSAGING_SOCKET` ([Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)). An `asyncRewake` hook that exits with code 2 "wakes Claude immediately even when the session is idle" ([Claude Code hooks reference](https://code.claude.com/docs/en/hooks)). Channels let an MCP server push events into an open session, and ship Telegram and Discord plugins. They are a research preview, need several setup steps, and "Claude Code doesn't acknowledge notifications" ([Channels](https://code.claude.com/docs/en/channels); [Channels reference](https://code.claude.com/docs/en/channels-reference)). Every route carries the same rule: an incoming message "can't approve anything" and "Permission prompts still fire" ([Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)).

The same documentation lists limits that bear directly on our failures at four to five concurrent loops. Cross-session messaging enforces per-sender rate limits, refuses bursts, drops identical repeats and queues at most **50** messages, so "a message loop between two sessions therefore stops on its own". A session that holds inbound messages for approval cannot show the approval dialog inside the Desktop app or VS Code, and **held messages there expire after five minutes** ([Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)). Monitor watches end after five minutes by default and thirty at most, with one notice to restart ([Claude Code tools reference](https://code.claude.com/docs/en/tools-reference)). Hermes stops bot-to-bot chains at `max_hops`, **default 4** ([Hermes messaging docs](https://hermes-agent.nousresearch.com/docs/user-guide/messaging)). Telegram caps a bot at 20 messages a minute in a group ([Telegram Bots FAQ](https://core.telegram.org/bots/faq)). No vendor publishes reliability figures for any wake path. The products report trigger misses, such as a Cursor automation that never fired for a ticket created by another automation ([Cursor forum](https://forum.cursor.com/t/automation-not-triggering-when-slack-workflow-creates-linear-ticket/155094)). Some limit wake storms on purpose: Factory deliberately does not trigger on Slack thread replies ([Factory docs](https://docs.factory.ai/software-factory/automations.md)).

### Codex can be woken, but not inside the desktop thread the human is watching

Codex's only documented in-app coordination is parent-child subagents ([Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)). Since about August 2026, though, `codex queue` has been a **stable** command that queues text for an existing session "by UUID or exact name" ([Developer commands](https://learn.chatgpt.com/docs/developer-commands?surface=cli)). A tutorial reports that "an idle session can wake when it receives a queued message" ([proflead](https://proflead.dev/posts/openai-codex-agents-dashboard-codex-queue/)). It has no reply or acknowledgement channel ([Issue #54252](https://github.com/openai/codex/issues/54252)). The desktop app is the obstacle. It runs its app-server "over a private stdio socketpair, so no other local client can connect to it". A second process touching a thread the app has open fails with "already has an active writer". An OpenAI maintainer stated the design assumption: "only one client will interact with a thread at a time" ([Issue #54683](https://github.com/openai/codex/issues/54683); [Issue #21551](https://github.com/openai/codex/issues/21551)). The reports conflict on one point that matters for us. One commenter on Windows Desktop reports `codex queue --thread` reaching *loaded* sessions, while others report no admission result ([Issue #54683](https://github.com/openai/codex/issues/54683)). The only other route reported to land in a desktop thread is a `UserPromptSubmit` hook, which delivers only when the human next types ([Issue #54683](https://github.com/openai/codex/issues/54683)). Live co-presence does work when every client attaches to one shared app-server, which the CLI's `codex agents` dashboard and `--remote` mode already support ([Codex App Server docs](https://learn.chatgpt.com/docs/app-server.md)). Our Codex watch is not bound to its session because the desktop app does not let anything bind to it.

## A tool boundary keeps one agent's turn intact; nothing protects the turn order across agents

Within a single agent the field agrees: a human's mid-task message waits until the running tool call finishes, then joins the turn. GitHub documents it plainly: "Copilot implements your input after it finishes its current tool call", and adds that steering "is not available for third-party coding agents" ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents)). Claude Code, Hermes (`/steer`) and OpenClaw's default queue mode behave the same way, and each offers a separate action for a hard interrupt ([Hermes slash commands](https://hermes-agent.nousresearch.com/docs/reference/slash-commands); [OpenClaw queue and steering](https://docs.openclaw.ai/concepts/queue-steering)). LangGraph makes the pause explicit with `interrupt()` and resumes against a checkpoint ([LangChain docs](https://docs.langchain.com/oss/javascript/langgraph/add-human-in-the-loop)).

Across agents, the field avoids crossed turns structurally and does not try to resolve them. In Microsoft's group chat one selector owns the turn order, so a human is just another participant in a single sequence ([MS Learn](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/group-chat)). In Claude Code agent teams, when you view a teammate, "plain text and skills go to that teammate, and built-in commands go to the lead's session". Every teammate's permission prompt still surfaces in the lead ([Agent teams](https://code.claude.com/docs/en/agent-teams)). That gives us a working rule: the human may talk to any agent, while turn state and authority stay with one owner. Antigravity inverts the flow, with agents posting requests to a single Inbox ([Google Developers Blog](https://developers.googleblog.com/build-with-google-antigravity-our-new-agentic-development-platform/)). Devin gives a link per child and leaves reconciliation to the coordinator ([Cognition blog](https://cognition.com/blog/devin-can-now-manage-devins)). No product documents what happens when a human directs worker B while the hub believes B is waiting on worker A. Interjection is always addressed to one agent, never reconciled across a team. The research is thin too. A June 2026 preprint found intervention timing a "low-reliability construct" on which human annotators disagree ([arXiv 2606.04296](https://arxiv.org/pdf/2606.04296)). A long-horizon benchmark now treats mid-task user interruptions as a core mode ([arXiv 2604.00892](https://arxiv.org/pdf/2604.00892)). Yet the researchers found no study of interruption costs in multi-agent LLM systems, and none of voice-directed multi-agent work.

## Setup is light only where agents live inside tools people already use

The lightest designs ask the user only to assign or mention something in a tool they already use, after an admin has configured things once. Agent HQ puts third-party agents behind settings toggles on a paid Copilot plan ([GitHub Changelog](https://github.blog/changelog/2026-02-04-claude-and-codex-are-now-available-in-public-preview-on-github/)). Factory has admins set the model, instructions and service account once, after which users only assign or mention ([aiposthub](https://www.aiposthub.com/factory-delegations-slack-linear-identity-review/)). Inside Claude Code the burden ranges from zero to high. Cross-session messaging needs nothing. Remote Control is one command on a claude.ai login. Agent teams need an environment variable and, for split panes, tmux or iTerm2, which rules out Windows Terminal. Channels need a bot token, a plugin install, Bun, a flag hidden from `--help`, pairing, and admin enablement on Team or Enterprise plans ([Channels](https://code.claude.com/docs/en/channels); [Agent teams](https://code.claude.com/docs/en/agent-teams)). Anything cross-session in Codex means experimental app-server flags, token files and generated schemas, and integrators report no documented way at all to attach to the desktop app ([Codex App Server docs](https://learn.chatgpt.com/docs/app-server.md); [Issue #40134](https://github.com/openai/codex/issues/40134)). Hermes needs a model provider, platform credentials, an allowlist and a service install, softened by a setup wizard ([Hermes messaging docs](https://hermes-agent.nousresearch.com/docs/user-guide/messaging)). The frameworks are code-first and put speaker selection, termination and persistence on the developer. No usability study of any of these for non-technical users was found. The pattern that keeps the burden off end users is consistent, though: wire things once at install, then let users wake agents by acting on an artefact they already understand.

## Protocols settled on tools and context, and agent-to-agent remains an enterprise web-service problem

The Linux Foundation's Agentic AI Foundation now hosts MCP (agent to tool), AGENTS.md (repository instructions for coding agents) and, since August 2026, A2A (agent to agent). Its own framing is that the protocols "work together without forcing every system into one architecture" ([AAIF blog](https://aaif.io/blog/where-a2a-fits-in-the-open-agent-ecosystem)). A2A reached v1.0, which the Linux Foundation called its first stable specification in April 2026, with more than 150 supporting organisations and integration in Azure AI Foundry, Copilot Studio and Bedrock AgentCore. No production customers are named ([LF press release](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year)). One A2A package maintainer cites roughly **10.9 million** PyPI downloads for the A2A SDK against **257 million** for MCP, and several teams report reverting to MCP-style designs because A2A "just felt over complicated" ([Hacker News](https://news.ycombinator.com/item?id=48582679)). MCP's July 2026 revision moved further from peer messaging. It removed sessions, replaced server-initiated requests with client-retried "input required" results, and deprecated Sampling ([MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Zed's Agent Client Protocol does drive Claude Code, Codex and Gemini CLI from one editor, but it connects one human UI to one agent ([Groundy](https://groundy.com/articles/acp-registry-is-live-zed-and-jetbrains-just-did-for-ai-agents-what-lsp-did/)).

The vendors' own stances make the cross-vendor gap explicit. Anthropic's doctrine is "To involve a different tool, expose it to Claude as an MCP server", and it has made no public statement on A2A ([Run agents in parallel](https://code.claude.com/docs/en/agents.md)). OpenAI co-founded AAIF with AGENTS.md, removed `codex mcp-server`, and left Codex reachable only through its app-server ([OpenAI](https://openai.com/index/agentic-ai-foundation/); [Developer commands](https://learn.chatgpt.com/docs/developer-commands?surface=cli)). The genuinely cross-vendor artefacts in coding are therefore an instruction file and a git repository. That is our substrate, and it is not a stopgap.

## Git is the only record the user owns, and almost nobody isolates the reviewer

### Products keep the agent conversation in vendor stores

In the products, the durable record is the git and pull-request trail plus a vendor-hosted session log. GitHub links the two most cleanly: each commit carries an `Agent-Logs-Url` trailer, and stopped sessions "can be archived but not deleted" ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents)). Devin and Amp give shareable session links. Amp withdrew public thread sharing because threads can contain source code, command output and credentials, which shows that richer logs are also more dangerous ([Amp docs](https://ampcode.com/docs/collaborate/thread-sharing); [Aurascape](https://aurascape.ai/?p=8281)). Claude Code agent teams keep mailboxes and task lists as runtime JSON under the user's home directory. The team config is removed at session end, and teammates are not restored on `/resume` ([Agent teams](https://code.claude.com/docs/en/agent-teams)). None of the products found makes the agent-to-agent conversation itself a first-class, exportable, user-owned artefact. The closest published analogue to ours is a single-author preprint. It reports that a git-stored, append-only, signed event log cut duplicated work from **78% to 0%**, against a file-based tracker that lost concurrent writes ([Sarkar, arXiv 2606.19616](https://arxiv.org/abs/2606.19616)).

### Different models review, but they read the author's framing

Separate reviewers are spreading: Jules has a Planning Critic, Copilot's coding agent has a built-in review step, and Amp's Oracle runs on another vendor's model ([Jules changelog](https://jules.google/docs/changelog/2026-01-26-1); [GitHub blog](https://github.blog/news-insights/product-news/welcome-home-agents/); [Amp: Oracle](https://ampcode.com/news/oracle)). Isolation from the author's conclusion is almost never documented. In Microsoft's writer-reviewer sample "all agents see the full conversation history", and the Reviewer's word "approve" ends the run ([MS Learn](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/group-chat)). That matters because anchoring is strong. In an adversarial study, commit messages framing code as correct got vulnerabilities past Claude Code review **88%** of the time and past Copilot **35%** ([arXiv 2603.18740](https://arxiv.org/html/2603.18740v1)). A March 2026 paper argues same-session review is confirmation-biased and proposes separate production and review contexts ([arXiv 2603.12123](https://arxiv.org/pdf/2603.12123)). Debaters drift toward the majority and toward a single high-capability peer ([arXiv 2506.01332](https://arxiv.org/html/2506.01332v1)), and hiding authorship is the proposed counter ([arXiv 2510.07517](https://arxiv.org/pdf/2510.07517v4)).

The case that cross-vendor review is better is real but contested. Judges favour their own model family ([arXiv 2604.11589](https://arxiv.org/pdf/2604.11589)), but an EMNLP 2026 Findings paper argues much of that effect disappears once output quality and judge severity are controlled ([ACL Anthology](https://aclanthology.org/2026.findings-emnlp.1571.pdf)). At matched compute, multi-agent debate "often fail[s] to outperform" self-consistency, though model heterogeneity consistently helps ([Zhang et al., arXiv 2502.08788](https://arxiv.org/html/2502.08788v3)). Diverse teams outperform homogeneous ones under judge-based selection but show no advantage under majority voting ([arXiv 2603.20324](https://www.alphaxiv.org/abs/2603.20324)). Heterogeneity is worth most when the reviewer judges or selects. Seeking consensus wastes much of it. No study found measures the catch rate of cross-vendor against same-model review on real artefacts.

## What is settled, what is argued, and what is open

| Area | Established practice | Contested | Unsolved |
|---|---|---|---|
| Topology | Orchestrator-worker for parallel breadth; hub forwards verbatim; one owner per piece of work; 3-5 workers per hub | Whether peers beat a supervisor; whether multi-agent helps coding at all | Switching between star and peer at runtime |
| Waking | Platform event on a durable artefact; dial-out gateways; delivery at the next tool boundary | Push against poll reliability, since nobody publishes figures | Acknowledged delivery; waking another vendor's desktop session from outside |

| Review | A separate reviewer, often another model; separate review context | Size of self-preference bias; value of debate at matched compute | Measured catch rate of cross-vendor review; reviewer isolation from the author's conclusion |

## What this means for our loop

### Where we are ahead

Our ticket, whose status names the seat whose turn it is, is the platforms' "artefact is the protocol" pattern without the platform. It extends A2A's input-required state from two parties to several seats, and it does so in a record the user owns, readable by any vendor's agent. No product keeps the agent-to-agent conversation as a portable record, so this is the strongest position we hold. Our authority rule, that a peer's relayed go-ahead is data and never consent, is the same line Claude Code draws on every inbound route ([Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)). Our wakes already hand over the last few turns and a short statement of the rules, which follows the field's advice to deliver context with the wake rather than tell the agent to go and find it. Cross-vendor review is something only Amp offers by design, and the debate literature backs it when the reviewer adjudicates instead of converging.

### Where we are behind

**Codex is the largest gap, and the fix is to choose a route, not to wait for OpenAI.** The cheapest experiment is to have the Codex watcher run `codex queue --thread <exact name>` against the loaded desktop thread on Windows, since that is the one configuration reported to work ([Issue #54683](https://github.com/openai/codex/issues/54683)). If it fails, the operator's presence turns a weakness into a workaround. A `UserPromptSubmit` hook that injects the pending ticket whenever the operator says anything to Codex removes the content of the relay, leaving the operator only a "go". The structural fix is to run the Codex seat in the CLI against a shared app-server (`codex agents`, `--remote`), where external turns appear live ([Codex App Server docs](https://learn.chatgpt.com/docs/app-server.md)). An outer `codex exec resume` supervisor is not an option while the desktop app holds the thread, because it is refused as a second writer.

**Our wakes need the bounds every product ships.** The field caps concurrency at roughly three to ten workers per coordinator, Kim et al. find per-agent capacity thinning past three or four, and MAST puts about a third of failures in repetition and termination ([Cemri et al.](https://arxiv.org/html/2503.13657v3)). Failure at four to five concurrent loops is the expected outcome for a design that has one watcher per loop and no coalescing. The field's pattern is one doorbell per seat that multiplexes every ticket addressed to it, coalesces duplicate rings the way OpenClaw's wake endpoint returns "coalesced" ([OpenClaw webhooks](https://docs.openclaw.ai/automation/cron-jobs/webhooks)), and re-reads the record on a heartbeat, because no push path acknowledges delivery. Each conversation also needs a round budget, the equivalent of Microsoft's iteration cap.

**The operator lacks an inbox.** Antigravity's single Inbox and Claude Code's agent view, with its "Needs input" state and notifications ([Agent view](https://code.claude.com/docs/en/agent-view.md)), give the human one place to see who is waiting. Tickets whose status names the operator already contain that list. Spoken through the hub on request, they would replace the operator remembering which seat is stuck.

### What we may be overlooking

**Some of our wake failures may be the platforms' own loop guards working as designed.** Claude Code drops identical repeated messages, rate-limits each sender, refuses bursts, and expires held messages after five minutes in the Desktop app. Hermes stops bot-to-bot chains at four hops by default. A fleet of near-identical doorbells from one sender at four or five loops is precisely the traffic these guards exist to stop. This is an inference from the documentation, not an observed cause. Before redesigning, we should check whether our doorbells vary their text, whether the Claude desktop session holds inbound messages, and whether any chain through Telegram exceeds four hops.

**Crossed turns are a design gap, not operator error.** The field's only working answer is that one owner holds turn state while anyone may speak to anyone. When the operator speaks directly to a spoke, that spoke should record the operator's words in the ticket as a note to steer by, not as a new turn, and only the ticket's status should move the turn. The hub then reconciles from the record instead of from memory. This keeps the voice path to any agent open without letting it fork the turn order.

**The hub's dual role compromises the peer review we value.** Our hub briefs the work, reads the author's account of it, and then reviews it in the same context. That is the setup the 88% anchoring result and the cross-context review paper warn about, and Cognition has the agent that holds the task context decide which review findings to act on, not the reviewer ([Cognition](https://cognition.com/blog/multi-agents-working)). If cross-vendor review is to work like scientific peer review, the reviewer should start in a fresh context. It should receive the artefact without the author's claim that it is correct, and record a verdict before reading the author's reasoning. The hub's own work should be reviewed by a spoke. We should also measure what reviews catch against a same-model baseline, because the literature has no such number and ours would be the first.

**The road to peers runs through separating authority from messaging, not through a switch.** Claude Code's agent teams already show the target shape: peers message each other directly while a fixed lead holds permissions and consent. Our ticket record supports the same split, since any seat can address any seat while the operator's signed rulings and the run's named owner keep the star intact. Peer mode can then be widened one bounded task at a time, each with a named owner, a verifier and a round budget, which are the conditions under which Anthropic's flat compiler run worked and Cursor's flat design did not.

## Conclusion

The field's leaders have not converged on agents talking to each other. They have converged on agents being woken by changes to a shared artefact, with a single owner for each piece of work and a single place for the human to act. That reframes our redesign. The open question is not which protocol should carry agent conversations, because none of the protocols fits live local sessions and the vendors are not building one. The open questions are how a seat is reliably and boundedly told that the record changed, and how the human's voice enters the record without forking the turn. Both have small, local answers: a coalescing doorbell per seat, a heartbeat, a round budget, a Codex route the desktop app actually permits, and an operator note that steers without taking a turn. Those can be built without waiting for any vendor.

The part where we can lead rather than follow is the one the field has not measured: whether review by a different vendor, isolated from the author's conclusion, catches more than review by the same model. Every product now offers "a different model reviews", and none has shown that independence survives a shared context. A git record in which every review, its inputs and its verdict are committed is the right instrument to answer that. Making the reviewer blind before we scale the loop would turn a value we hold into evidence.
