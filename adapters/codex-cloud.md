# Codex Cloud workspace setup

This optional route prepares the GitHub repository Codex has already checked
out. It uses the existing Codex lifecycle adapter independently; VM preparation
does not install project hooks, grant trust, or prove agent receipt of Tier 0.

From a clean framework checkout whose HEAD is published:

```powershell
& .\tools\mdllm.ps1 cloud configure domain\my-domain --harness codex
```

On Linux/macOS use the framework's floor-capable Python with `tools/mdllm.py`.
The output lands privately under `.bundle-build/codex-cloud/<domain>/` and
contains `.codex/cloud/` plus `.agents/skills/configure-codex-cloud/`.
`--out <domain>` writes directly to the owning domain after source verification.
Files that already match are left alone; different existing bytes are refused.
For upgrades render into a fresh output directory and review the diff. Use
`cloud check <domain> --harness codex --out <domain> --config <manifest>` from
the pinned framework to check every generated byte. `--preview` permits a clean
unpublished framework commit only in the private build directory, with an
explicit release-required marker; it cannot install into a domain.

The manifest uses strict JSON so its pre-framework reader needs no dependencies.
It declares the full framework commit, credential-free repository URLs,
workspace base and PR publication mode. The generator derives the repositories
and pin from Git; the operator supplies only choices that cannot be derived.
Unknown keys, duplicate keys, moving refs and credential-bearing URLs refuse.

Commit the reviewed files to the **domain repository**, then make them available
on its default branch under that repository's publication policy. Codex builds
the cache on the default branch before selecting the task's branch. In the
environment settings, set the workspace base to `/workspace/MarkdownLLM/domain`,
Manual setup to `bash .codex/cloud/bootstrap.sh`, and maintenance to
`bash .codex/cloud/bootstrap.sh maintenance`. The alternative conventional
`domains` spelling is accepted via `--workspace-directory`. The repository is
cloned under that base; do not include its name in the workspace setting.

The bootstrap downloads the exact public framework into a temporary sibling,
checks isolation and collisions, then surrounds the existing domain checkout.
It never moves that checkout or changes its HEAD, index, entry contract or
tracked files. It creates a private framework virtual environment, pins PyYAML
6.0.3, and calls the framework-owned `cloud prepare` service to install the
normal Git hook set. Operator-owned hooks are preserved by the shared installer.
Framework pin drift, dirty cached substrate or foreign files refuse and explain
the remedy. A new pin requires a deliberate environment cache reset.

Preparation validates domain content. Session-gate findings are reported as
deferred to agent startup; all other validation Errors fail setup. No session
attestation is written, and the commit hook retains its ordinary strict gate.
The working agent follows the domain entry contract: sync, then emit and read
`session-start . --contract`, including the kernel integrity trailer, and load
the routed skills. Setup logs cannot substitute for this. Git-hook execution
is exercised in isolated integration tests; live cloud delivery and lifecycle
trust require a separate real task before claiming compatibility.

PR mode installs the clone-local `mdllm.publication=pr` restraint recognised by
the shared publication reader and doctor. It only reduces authority; the
domain's committed `git.autopush` declaration remains unchanged. The host's PR
workflow carries publication. This is not a security sandbox against a user
deliberately running Git; an explicit one-shot `mdllm publish --authorize-once`
still names its own human authority and retains all ordinary branch guards.

The generated configuration skill turns a conversational request into the
renderer plus the supported Codex settings UI. It reads settings back after
saving and keeps login/repository authorisation with the user when required.
It does not depend on a private environment API. The Agents API's hosted
environments are a separate product route and are outside this adapter.

Official contract: [Codex Cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environment).
